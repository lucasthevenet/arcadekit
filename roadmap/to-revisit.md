# To revisit before a stable release

Not a milestone of the [roadmap](../ROADMAP.md): a list that is added to as the work goes, and gone through before the first stable version. Each line is a thing that goes wrong with no error, and that only someone who knows how the inside works would avoid: nothing in the types or at run time stops it, and a sentence of its guide is all there is. Before a stable release each one is closed, by code that stops it or by a design that leaves no room for it, or kept on purpose and said plainly where a game's author will read it.

When you come across one, while building, testing or writing a sentence of a guide that begins "it is the game's to", add a line under its area in the same commit, with what would close it if you know. When a line here is closed, take it out in the same commit. What is merely not built yet is not here: that is the site's [Not done yet](../website/src/content/docs/not-done-yet.md).

Before changing an area, read its section: these are the mistakes the code will not stop.

## The order systems run in

- **`System.before` and `System.after` move a system past everything listed in between.** One that says `System.before(other)` is pulled ahead of where `other` was listed, and with it ahead of every system listed between the two, which said nothing; and a plugin's systems are listed before the app's own. Adding such a system leaves the others in the order they were, which is the point, but the one that moved may now run before something it reads from. What a frame draws with no longer does this: a renderer's last step is in `"postFrame"`, and nothing has to say `before` it. `app.conflicts` finds such a pair when both systems have said what they read and write, with `System.access`; one that has not is in `app.undeclared` and in no check. To close it: have every system say, which would break every game that has one that does not.
- **A system that reacts through a change query, listed before the system that makes the change, reacts a tick late.** In a game that ticks when needed, one such system gets the one tick that follows the last and two in a row are a tick short: the game rests with work undone, unless the system that changed something asks for a tick with `Ticks.more`. `app.conflicts` lists the pair, as one that `"watches"` and one that `"writes"`, when both have said what they read and write; it does not say which way round is right, and an order that was said the wrong way round is taken at its word.
- **What a system said it reads and writes is held as it runs, and no sooner.** A system that touches something it left out only when some condition of the game holds is refused in the first tick in which it does, which may be an hour into a game and never in a test. To close it: nothing short of proving it from the system's types, which do not carry it.
- **A despawn is said by one component.** A system that despawns an entity says it writes a component the entity has, and the entity's other components go with it, as does whatever hangs from it by a relation. A system that visits those through components the first never named is not found to be in conflict with it.

## Ticks, frames and real time

- **A system that has work every tick and does not say so stops when the game rests.** A game that ticks when needed rests when the app sees nothing waiting: actions, states, scripts, events, and what a system said with `Ticks.more`. A system that counts a clock down in a field and never asks is not told apart from one with nothing to do, and nothing says so. To close it: nothing cheap is known. The world's hash before and after a tick would tell, at the cost of a hash a tick.
- **A tick reads the devices unless it is told not to.** `App.replay` tells it, and a session's own ticks read none. Whatever else runs a game again from a log by hand, a tool, has to say `{ input: false }` itself, or the keys of the machine it runs on are reported into the game it is re-running, and nothing says so. And a game that steps its app by hand still has to run a tick when its UI has sent something: nothing ticks for it.
- **`smooth: true` draws a tick behind.** A game stepped by hand and drawn with `app.frame(0)` shows the tick before the one it just ran. A test that looks at what is drawn has to know.
- **`Effect.sleep`, a promise, or any wait in real time resumes outside the tick**, and a fiber started with `Effect.forkDetach` is not watched by the app. Either changes the game at a moment no replay repeats. Scripts wait with `Script.nextTick`, `Script.sleep` or an event's `wait`; nothing refuses the others.
- **`Assets.load` in a script** resumes in whatever tick the file arrives in. It is not refused there.

## Several peers

- **A layer that listens, provided to one line, is gone with that line.** `Transport.layerBroadcastChannel` or `Transport.layerWebSocket` provided to `Transport.connect` alone closes its channel as soon as the session is joined. Each says so when it is next used, which is the first tick; a transport of the game's own made with `Transport.text` says nothing unless the game makes it.
- **A socket that drops ends the game over it.** `Transport.layerWebSocket` does not connect again, and a peer that came back would have missed messages nobody sends twice. The peer whose socket closed is told, with `Transport.Closed`; the others are told nothing and wait. To close it: messages kept until the other side has said it has them, and a relay that says who has left.
- **A relay vouches for the name a peer connected under, and nothing asks whether the peer may have it.** `Relay.join` lets in whoever asks first under a free name: a host that does not check the request before it calls `join` has a relay on which anyone is anyone. And a transport that is not a relay's, a `BroadcastChannel` or one made with `Transport.text`, vouches for nothing: a peer can speak in another's name there, and the peers stop as drifted, with a report that says a tick and not that someone lied. To close it: a way to hand `join` proof of who is asking, or messages that are signed.
- **A payload its schema refuses is refused on the peer that issued it alone.** It has no JSON form to send, so the other peers never hear of it, and the `Action.Rejected` it becomes is an event on one machine. A system of the tick that reads that event and writes what it read has the peers come apart. To close it: refuse such a payload where it is enqueued, as a value or by throwing, in a game of one too.
- **Not everything that makes peers alike is compared.** Each peer is told its own plugins, seed, `delta` and names. Another seed, or a world that does not start the same, is found before the first tick, since the peers compare the hash they start from. Another `delta`, a system one peer lacks, or another list of names is found only when it has changed a world, at the checkpoint after: and a list of names that leaves a peer out is never found, since that peer is not heard. To close it: have the peers compare a hash of what they were made with, the names and the delta among it, with the state they start from.
- **A rewind starts each plugin's scripts again, and stops the ones started by hand.** A script that keeps its place in its own variables plays its part twice, on the peer that went back and not on the one that did not: the peers come apart, and drift detection says at which tick and not why. To close it: refuse a rollback session for an app that has scripts, or keep a script's place where a moment can hold it.
- **What a service of the game's own holds is not put back by a rewind**, as it is not saved: a count kept in a layer goes on from the future that was given up. Nothing tells a service that the game went back.
- **What the frame stage did for a tick that is run again is done again.** A sound is played twice, and a UI is told of a score that is then taken back. The frame stage is not told which ticks are final: a game asks its session, `session.confirmed`.
- **What the hash does not cover can differ between peers for as long as it does not reach the world**: the events waiting to be read, what a change query has yet to visit, a system's own variables, a service's state. The report then names the tick it reached the world, not the tick it began.

## What a replay, a save and the hash do not hold

- **A write through a raw column is not seen by anything.** In the frame and input stages it changes the game unless `verifyFrames` is on; through a query that says it only reads, it is written all the same; and no change query hears of it.
- **A refused action does not undo what is outside the world**: an object in a field changed in place, a call to a service of the game's own, a script it started.
- **A save holds no scripts, and the log does not say when one was started by hand** or the delta and number of ticks it was recorded at. Whoever loads or replays has to know and supply them.
- **The hash is of the world only**: not the events waiting, what change queries have yet to visit, the actions queued, or how far a script has got. Two games with the same hash can go different ways.
- **A waiting event's payload is not checked when a save is loaded.** After a change to an event's schema, a save that holds one in the old form loads, and the event throws when a system first asks for it. To close it: decode the waiting events as the save is loaded, and refuse the save with the reason.

## Values that have to be right and are not checked

- **A `Transform3d.Scale` or `Transform2d.Scale` added with no value is all zeros, and its entity is drawn as nothing.** A component added with no value is zeros, which is a place and a turn that are right and a size that is not. To close it: a component that can say what it is when nothing is said, or a renderer that says so once.
- **An entity with both a `Transform3d.Position` and a `Transform2d.Position` is drawn from the first**, and its `Transform2d` rotation and scale are then not read.
- **What a frame that failed said of a channel stands until a frame ends.** Systems that say something else of it in the next frame are refused as if two had spoken at once, unless the failure was that refusal itself. A game under a driver stops at a failed frame; a test that steps on after one has to know.

## Who lets go of what

- **A geometry and a material given to `Three.instances` are the game's to dispose of**, and so is whatever `make` of `Three.objects` made, through `free`. Nothing here does, and nothing says when one was forgotten.
- **A loader of Three.js that fetches for itself** does not go through `Assets.Loader`: a test's files in memory do not serve it, and an interrupted load does not give those requests up. A glTF model's own files no longer are such, since `Gltf.model` fetches them; what is left is the decoder a compressed model is given in `prepare`, and any asset of the game's own made around another loader, an FBX's, say. A streamed track, `Browser.stream`, is fetched by the page in the same way, on purpose: a test that provides files in memory hears nothing of it and has to play a clip of its own.

## Reported, and not settled

- **A page's sound after a laptop's lid was shut and opened.** With the example page of `arcadekit` on a MacBook: music playing, the lid shut and opened, the game played again, and the sound took a moment to come back and then came with its first notes all at once, as if they had been queued. Other apps on the same machine did not do it. One cause was found and closed: cues played while the page's audio was asleep or still waking were started all the same, and were heard together when it woke; they are dropped now. That was reproduced only with an audio made slow to wake in headless Chromium, never with a real lid, and it was not heard again on the machine after the change. Before a stable release: shut a real lid, on more than one browser, and listen. If it is still there, look at what the audio's clock does across the sleep (`currentTime` against the wall clock, and `state`), and at whether the looping track should be started afresh when the page is seen again in place of being woken.
