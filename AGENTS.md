# arcadekit

## Project status: alpha

arcadekit is alpha. Nothing depends on it in production yet: no players, deployments or users to protect. Breaking changes are fine when they improve the code, and a better design wins over compatibility. That covers API changes, renames, removing or reshaping exports, changing stored data formats or localStorage keys, and large refactors.

- Don't add compatibility shims, deprecation paths or data migrations. Change the code and update its callers. A rename moves every caller and every living doc; the records keep their wording ([`docs/code-style.md`](docs/code-style.md), "Names").
- Still say what breaks: in the commit message, in the PR description, and, for the published `arcadekit` package, in its changeset (a minor bump while below 1.0).
- Keep the replay and determinism hashes unless a change to the simulation's rules is the point.

## A game is declared

A game is written as **declarations**: one named class per part, hosted by a Layer or a loop ([ADR-0020](docs/adr/0020-a-game-is-declared.md)). They are `Game.Event`, `Game.Command`, `Game.Rejection` and `Game.Simulation` (`arcadekit/game`), `Game.Engine` (`arcadekit/game/browser`), `Content` and `Asset` (`arcadekit/content`), `Coop` (`arcadekit/net/browser`, [ADR-0021](docs/adr/0021-co-op-is-declared-from-the-games-engine.md)), `Save` and `Setting` (`arcadekit/save`), and `CueTable` (`arcadekit/audio`). Push-puzzle and its demo are the example to copy, and [the entry's README](packages/arcadekit/src/game/README.md) shows each block.

- **A new part a game supplies is a declaration**: a builder `(name, definition)` that returns a class with the definition as statics, typed by an explicit `XClass` interface. If it has a service, the class is its key and a `layer` provides it.
- **Handlers inside a declaration are plain functions** (`create`, `step`, `apply`, `view`, `input`). What hosts it is Effect, or plain code as `Game.Loop` is. `step` and `apply` change the state in place and return nothing (`apply`, or a rejection): anything else is a type error, and `Game.Loop` throws on it.
- **A run changes only at a step**: by its input, and by a `Game.Command` the loop applies at the start of the next step. An `apply` handler takes its command or refuses it by returning one of the `Game.Rejection`s the command declares, and the sender's `engine.send` fails with it.
- **Rules are checked with scenarios** (`arcadekit/game/scenario`).
- **Kit source names a declaration's base first**, as `audio/audio-system.ts` does for its `AudioLoadError`, since it is checked with `isolatedDeclarations`. Genre packages and apps write `class X extends Game.Event(...) {}`.
- **Co-op is declared from the game's engine**: `class SurvivorsCoop extends Coop("SurvivorsCoop", { engine: SurvivorsEngine, ... }) {}`. The class is the key of the Co-op client and its `layer` provides it over the app's `CoopRooms`; the engine's `view` is told the local player (`{ local }`) by both hosts; and an app turns what a seat reports into Messages with the class's `match`, the run's events under `run`. Its lockstep run steps the game's declared simulation through `Game.Loop`, and what a co-op player decides is one of that simulation's commands, sent with the client's `send`: it rides the player's next step to every peer. Nothing of the older contract is left in the kit's entries (`makeGameEngine`, `GameSimulation`, the `runtime` entry). New work goes on the declarations.

## Adding to the kit

Before adding or reshaping a module of the kit (a declaration, what hosts one, a service, an entry's exports), read [`docs/code-style.md`](docs/code-style.md): what kind of module it is, the shape of a declaration, its names and types, and when it is done. Lint and `packages/arcadekit/test/style.test.ts` check part of it, and the page says which part.

## Effect and plain code

Every module of the kit has Effect's shape ([`docs/code-style.md`](docs/code-style.md), "An Effect module"). Whether its code is Effect or plain is decided by one question: would we write it plain if performance were free? ([ADR-0024](docs/adr/0024-the-kit-is-written-as-effect-modules.md), which amends [ADR-0017](docs/adr/0017-effect-at-the-edges-plain-code-inside.md).) Code stays plain only for correctness, and these are the reasons:

1. **The same bits on every peer.** A step gives the same result on every peer and every replay, so it reads no clock or random source of its own: its time comes in as an argument and its randomness from the run's seeded `Rng`. Never use Effect's `Clock`, `Random` or `DateTime` there, nor `Date`, `Temporal`, `performance`, `crypto` or `Math.random`. Lint enforces this.
2. **It finishes in the call.** A step finishes inside the frame or tick that runs it, and a frame draws whole before the browser shows it. An Effect can't promise that: one that waits throws when run synchronously, and on a fiber the scheduler can cut a long run after 2,048 operations ([ADR-0020](docs/adr/0020-a-game-is-declared.md)).
3. **Pure data work**, of the kind Effect writes plain itself: its `Array`, `Number` and `MutableRef` are plain functions over data.
4. **A framework's contract.** Foldkit's `update` and `view` are pure functions; their side effects are Commands, Subscriptions and Mounts.

Cost is not a reason. Code that was plain only to save an allocation, a fiber per frame, tick or message, or an Effect per entity outside a step becomes Effect wherever Effect buys something: a lifecycle, interruption, a typed failure in place of a throw, a service, a stream in place of listeners, or a span. Where Effect buys nothing the code stays plain: don't add Effect for consistency alone. Performance is deferred, not ignored: run `pnpm bench` before and after a rework and give its numbers against [`docs/perf-baseline.md`](docs/perf-baseline.md) in the PR.

Plain on purpose, by entry. An entry still on `NOT_YET_EFFECT_STYLE` (`packages/arcadekit/test/style.test.ts`) keeps its line as ADR-0017 wrote it, cost reasons included, until its rework moves the line to ADR-0024's reasons:

- **`arcadekit/core`**, reworked: every file is plain, for 1 and 2, since a step calls it, and for 3. `entity-pool.ts`, `ring.ts`, `ring-reader.ts`, `tile-map.ts`, `layout.ts` and `internal/fields.ts` are typed arrays a step writes and a view reads; `spatial-grid.ts` answers a step's "what is near" with exact arithmetic; `fixed-step-clock.ts` turns a frame's time, given as an argument, into steps; `rng.ts` is the run's seeded randomness; `event-buffer.ts` holds what a step reports until its loop delivers it; `state-hash.ts` folds a state into the digest peers compare; `exact-math.ts`, `point2.ts`, `timer.ts` and `tween.ts` are the arithmetic a step or a view calls, exact by [ADR-0011](docs/adr/0011-a-step-uses-only-exact-math.md). None imports `effect` but for its module shape (`Pipeable`, `Inspectable`, `Predicate`, `Function.dual`).
- **`arcadekit/input`**, reworked: `input-controller.ts` is plain. Its reads (`axis`, `isDown`, `wasPressed`), `consumePresses` and `endFrame` run in the step loop that reads a step's input, for 2, and so do its gamepad polls: a pad's buttons and sticks are only polled, with no event to listen to. Its swipe test and axis arithmetic are data work, for 3. Its listeners write what they hear while the browser dispatches the event, for 2, as host events a frame reads as state do (below). A `Game.Engine`'s or a `Coop`'s `input` handler makes the controller with `InputController.make`, and its host's `acquireRelease` around the input source disposes it, as a resource a plain handler makes is (below). It imports `effect` only for its module shape.
- **`arcadekit/content`**, reworked: Effect, but for its data and what a game hands a declaration. A `ContentSource` value (its prototype, its guard) and `fromRecord`'s lookup are data work, for 3. A `Content`'s `validate` and an `Asset`'s `release` are a declaration's handlers, plain by ADR-0020: a load calls `validate` on what it decoded, and the layer's scope calls `release` in a finalizer. Keeping a load's first success is Effect (`Effect.cachedWithTTL`), and so is freeing it: the layer's scope holds the release (`Scope.addFinalizer`, which a closed scope runs at once). `FetchContentSource` wraps `fetch` and `response.json()` with `Effect.tryPromise`, aborts the request of an interrupted read, and fails a response that isn't a success with a `ContentError`, not a throw.
- **`arcadekit/save`**, reworked: Effect, but for its data and what a game hands a declaration. Its data work, for 3: a save's merge by id (`save.ts`), which an app's Foldkit `update` also calls as `MySave.merge`, for 4; `storedSave`, which builds the Schema of the stored save; and a `Stored` value (`stored.ts`: its prototype, its guard, `Stored.make`). A save's `mergeRecord` and a setting's `merge` are a declaration's handlers, plain by ADR-0020: a write calls one between its read and its store. `Setting`'s check of its `default` is a throw when declared, which refuses a mistake as the module loads. Reading and writing storage is Effect (`internal/keep.ts`, over the app's `KeyValueStore`): a failure is logged, never thrown or failed, a declaration's writes run one at a time (a `Semaphore`), and each read and write is traced under the declared name. `BrowserSaveStorage.layer` catches, as a cause, the defect Effect's localStorage layer makes of a browser that refuses localStorage, and is memory from then on.
- **`arcadekit/audio`**, reworked: plain where a sound view calls it, Effect for its loads and its lifecycle. An audio system's calls but `load` (`play`, `setLoop`, `playMusic`, `setVolume`, `setMuted`, `setDucked`) are plain, for 2: a sound view makes them in its `render`, inside the frame. So is what they do in the mixer (`audio-mixer.ts`: voice caps and gaps, jitter, bus gains and fades), data work for 3, and so are its host's controls, `AudioMixer.unlock` and `AudioMixer.setHidden`, which the browser calls from its listeners while it dispatches the event: state every later play reads. `AudioSystem.make`, `AudioSystem.applySettings`, `AudioSettings` and `CueTable`'s check of the sounds its `layer` is given are data work, or would only wrap a plain call in `Effect.sync`; the check throws as the app's module loads, refusing a mistake. A load is Effect (a `Cache` shares each file's decode) and is traced as `AudioSystem.load`. A mixer's lifecycle is its scope's: `AudioMixer.make` adds the finalizer that stops its voices, and reads Effect's `Random` once for its jitter, since a mixer is presentation and no step. In `arcadekit/audio/browser` the gesture listener is plain, since a browser lets audio start only during the gesture's own dispatch, as `setPointerCapture` must run in a `pointerdown`, and so is the `visibilitychange` listener, for the state it writes; the layer adds and removes them with `acquireRelease`, decodes with `Effect.tryPromise`, failing a response that isn't a success with an `AudioLoadError` rather than a throw, and closes the AudioContext in a finalizer that waits for it.
- **`arcadekit/render-three`**, reworked: plain, but for loading a sheet. Its drawing runs inside the frame the browser shows, for 2, and Effect would only wrap each Three.js call in `Effect.sync`: a batch's `push` and setters (`instanced-sprites.ts`), a tile layer's `draw` (`tile-layer.ts`), mesh instances' setters (`mesh-instances.ts`), a stage's `render` (`stage.ts`), a camera's placement (`camera.ts`, `pixel-camera.ts`) and a gait's `update` (`gait.ts`). A pixel camera's arithmetic, a gait, `SpriteSheet.frameAt` and `resolveTags`, the frame table and the drawing buffer's size are data work, for 3. A stage, a batch, a tile layer and mesh instances are resources a plain `view` makes: each has a plain `make` and `dispose`, and the engine's `acquireRelease` around the view disposes them. A stage's `ResizeObserver` writes the drawing buffer's size while the browser dispatches it, for 2, as host events a frame reads as state do, and a batch that snaps to screen pixels reads its camera in Three.js's `onBeforeRender`, a host callback inside the frame. `SpriteSheet.dispose` is an `Asset`'s `release`, plain by ADR-0020. Loading a sheet is Effect (`SpriteSheet.fromUrl`, `SpriteSheet.decode`): it fails with a `SpriteSheetError`, not a throw, aborts its request when interrupted, and closes an image an interrupted decode leaves behind (`Effect.callback`). `arcadekit/render-three/testing` is plain data work a test calls, for 3, and its `TestSpriteSheet.fromTags` runs the decode with `Effect.runSync`, as a test helper may.
- **`arcadekit/game`**, reworked: plain where a step or a frame runs, Effect where it waits or has a lifecycle. Plain for 1 and 2: a declared simulation's `create`, `step` and `apply` (`simulation.ts`), the loop that runs them (`loop.ts`, a host made with `Game.makeLoop`, whose command queue and `settled` callbacks are plain calls), the kernel under it (`internal/kernel.ts`, which no entry exports) and the scenarios that check them (`scenario.ts`), which run their script in one call and throw a `ScenarioError`. Plain for 1 and 3: the players' step input (`player-inputs.ts`), which every peer steps on. Plain for 2: a `Game.Engine`'s `view` and `input`, `Game.View` and `combineViews` (`view.ts`), and the frame sources, `animationFrames` (`frames.ts`) and `arcadekit/game/testing`'s `ManualFrames`, which runs a frame in the test's own call. The builders' checks when declared, and the loop's refusal of a handler's stray return, are throws that refuse a mistake. Effect: the frame loop (`frame-loop.ts`) waits on each frame with an `Effect.callback` that cancels the frame it asked for, then does the frame's work in one `Effect.try`, and never yields but to wait; a crash stops the run in its failure channel (`Effect.tapError`); the engine's methods are traced under the declared name (`Effect.fn`); and `AttachError`, `GameCrashed` and `CommandDropped` are `Schema.TaggedError`s. A listener (`engine.listen`) is a plain call inside the frame, not a stream, so it has heard a frame before a send that frame answered completes.
- **The simulation.** Each genre's step (`world.ts`, and survivors' `hero.ts` and `hash-world.ts`), a declared simulation's `create`, `step` and `apply` with the loop that runs them and the scenarios that check them (`arcadekit/game`, above), the step input built from the players' inputs (`player-inputs.ts` in `game` and in `net`), and the lockstep protocol (`packages/arcadekit/src/net/lockstep.ts`, which decodes its messages with Schema but ticks as plain code, and the codec of a player's step payload in `codec.ts`, since every peer steps on what it decodes). A step must give the same bits on every peer, and a step over many entities must not allocate per entity (an event is a class instance, so reporting one allocates, and events are rare). So it runs no Effect, and it reads no clock or random source of its own.
- **Per-frame drawing and input.** `arcadekit/render-three`'s drawing (above), the genres' views and sound views, a view's reads of a ring (`RingReader`), a `Game.Engine`'s `view` and `input`, `Game.View` and `combineViews`, the `FrameSource` adapter, an audio system's play calls (`arcadekit/audio`, above), the per-message channel code (`dataChannelText`, `linksTransport`), and what the Co-op client calls between steps: the local player's input source (a `Coop`'s `input`), and nothing else of the game's. None of it runs an Effect itself. The engine calls views and input from one `Effect.try` per frame (`arcadekit/game`, above). A lockstep run on a ticker is one `Effect.callback` whose ticks are plain calls, and messages reach the session through plain listeners. Their lifecycles are Effect: the engine makes and disposes views, input and listeners with `acquireRelease`, and each peer link's connection and channels have their own.
- **Rules behind an Effect shell.** `packages/arcadekit/src/net/browser/room-state.ts` and the signalling worker's `room.ts` (`packages/arcadekit/src/net/worker/`, the `arcadekit/net/worker` entry). They take inputs and return outputs, and a rejection is a value, not a throw. A shell does the I/O: `signalling.ts` for the client; in the worker, the Durable Object's Effects in `connections.ts`, which call the plain `sockets.ts` to carry out the room's outputs on the sockets. A room size no room can have is the one throw: it is a mistake in the app's setup, refused when the Worker's module loads.
- **Foldkit `update` and `view`.** Pure functions. Their side effects are Commands, Subscriptions and Mounts.

Everything with a lifecycle is Effect: loops, connections, timers, workers, resources and services. So is untrusted input (decode it with Schema where it arrives) and any failure a caller should handle (a typed error).

Where plain code and Effect meet:

- **Waiting on a host callback:** `Effect.callback`. The engine's frame loop waits on each frame this way, then does the frame's work in one `Effect.try`. A peer link waits for its channels to open the same way, and a lockstep run on a ticker is one `Effect.callback` that resumes when the run ends.
- **Repeating host events an Effect reacts to:** `Stream.callback` with `Queue.offerUnsafe` (`keyPresses`, which makes each key press a Message), or a `Queue` that the host's listeners feed with `Queue.offerUnsafe` (the signalling worker's sockets, the Co-op client's lobby links in `packages/arcadekit/src/net/browser/coop-client.ts`).
- **Host events a frame or a step reads as state:** plain listeners that write it while the browser dispatches the event, as `InputController`'s do (a key held, a drag). On a stream the write would wait for a fiber, which a browser resumes a task later (`setTimeout`), so a frame could read the state before an event that came first. And some work has to happen during the event's own dispatch, as `setPointerCapture` does in a `pointerdown`. Adding and removing the listeners is still a lifecycle: see the next rule.
- **A resource a plain handler makes:** what a declaration's `view` or `input` makes (listeners, a renderer) has a plain constructor and a plain `dispose`. The handler is plain (ADR-0020) and library code runs no `Effect.run*`, so it can't run a scoped constructor: give the resource none. Its lifecycle is its host's, which is Effect: the engine and the Co-op client make the handler's result inside an `acquireRelease` whose release calls `dispose`. `InputController.make` and `InputController.dispose` are the example.
- **Plain code a host calls that must run an Effect:** capture a runner once, then use it on each call: `FiberHandle.runtime` (the Co-op client forks its seats this way), or `Effect.context` with `Effect.runForkWith` or `Effect.runPromiseWith`.
- **A platform that owns the entry points:** run each one's Effect there. The signalling worker's entry points are in the kit, in `packages/arcadekit/src/net/worker/index.ts`, and nowhere else: its Worker runs each request with `Effect.runPromise`, and its Durable Object, whose connections outlive a request, builds one `ManagedRuntime` with the object and runs every entry point on it.
- **No other `Effect.run*` in library code** (`packages/*/src`; test helpers aside). That one file is the exception, since Cloudflare owns its entry points. The browser apps run their Effects through Foldkit's runtime.
- **Throws:** plain code that throws on an expected failure is wrapped once, at the boundary, with `Effect.try` into a tagged error. Any other throw is a bug, and the Effect around it reports it as a defect. A frame is the exception: one that throws ends the engine's `attach` with the typed `GameCrashed`, so the app can show it. Where a module of Effect's reports an expected throw as a defect, as `KeyValueStore.layerStorage` does a browser that refuses localStorage, the kit catches that cause around the module's Effect (`BrowserSaveStorage.layer`; [`docs/code-style.md`](docs/code-style.md), "Errors").

## One package, twenty entries

The kit is one published package, `arcadekit` (`packages/arcadekit`), whose entries live in `src/<entry>/` ([ADR-0018](docs/adr/0018-one-package-with-entries.md)). Inside it, import another entry by relative path to its public file (`../core/index`), never as `arcadekit/core`. `ENTRY_IMPORTS` in `oxlint.config.ts` lists which entry may import which, and lint enforces it: adding an arrow is a design decision, so say why in the PR. The genre packages and the apps import `arcadekit/<entry>`. `arcadekit/net/worker` is the one entry that runs on Cloudflare: `tsconfig.worker.json` checks it with Workers types and no DOM, and no other entry may import `cloudflare:workers` (`test/entry-packages.test.ts`). `arcadekit/game/testing` holds the frames a test drives an engine on, `arcadekit/net/testing` a Co-op game's test helpers (fake rooms, a manual ticker, the Clock and scheduler of a test on fake timers, a test game), `arcadekit/render-three/testing` a sprite view's (a sheet with no image, what a batch shows, two checks of a sheet's PNG), and `arcadekit/game/scenario` the scenarios that check a simulation; only tests import them. `arcadekit/render-three/testing` runs in Node and imports `node:zlib`: `tsconfig.node.json` checks it with Node's types beside the DOM's, `tsconfig.json` leaves its folder out, and the same test allows a `node:` built-in only in an entry that only a test or a script imports. `arcadekit/game/browser` has everything `arcadekit/game` has plus the engine, so a file imports one of the two as `Game`.
