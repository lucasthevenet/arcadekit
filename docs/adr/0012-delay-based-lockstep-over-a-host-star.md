# Co-op runs in delay-based lockstep over a host star

#25 makes survivors a co-op game for 2 to 4 players in different browsers. The kit already has what lockstep needs: a deterministic step with all randomness from the run's `Rng`, step arithmetic that agrees across JavaScript engines ([ADR-0011](0011-a-step-uses-only-exact-math.md)), one plain input value per step, and a DOM-free `GameLoop` whose `frame(input, { steps }, nowMs)` runs exactly the steps it is given ([ADR-0010](0010-a-game-is-a-simulation-and-a-presentation.md)). What was missing is the decision on how peers agree on each step's input, and what happens when they can't.

**Delay-based lockstep.** Each peer sends only its input, never positions or state. Every peer runs step N once it has every player's input for step N, so all runs stay identical. A peer samples its local input for step `N + inputDelay`, a fixed **input delay** of a few steps, so the input usually arrives before step N is due and stepping doesn't stall. The delay is a setting, tuned by measurement; 2 to 6 steps is 33 to 100 ms at 60 Hz. There is no prediction and no rollback: a step whose inputs haven't all arrived waits.

**A host star.** One peer, the **host**, runs the lobby and is the hub; every other **peer** connects only to the host. Each peer sends its inputs to the host. The host decides when a step's inputs are complete, merges them and relays the merged input for that step to every peer. Every peer, the host included, steps on merged inputs only. The host is the one authority on who is in the run, so it is the only peer that decides a step without someone's input (see drop-out, below).

**A new module: `@gamekit/net`.** It holds the lockstep engine and its transports.

- The lockstep engine knows no transport. Its interface takes a `Transport` that carries messages between the host and the peers. The seam is that `Transport` interface, with two adapters: an in-memory transport for tests, with simulated latency, jitter and loss, and a WebRTC data-channel transport for the browser.
- The engine's merged inputs reach `GameLoop` as a plain `StepInput`, a buffer of confirmed inputs that `read(stepIndex)` indexes by step number. The engine calls `loop.frame(confirmed, { steps: ready }, nowMs)`, where `ready` counts the steps whose merged input has arrived. It steps on a timer, not on `requestAnimationFrame`, and a sibling of `GameDriver` draws on `requestAnimationFrame` only. This is the third stepping adapter on `GameLoop.frame` that ADR-0010 left room for, and no contract in `@gamekit/runtime` changes for it.
- `@gamekit/net` may depend on `@gamekit/runtime`, `@gamekit/core` and Effect. Nothing lower imports it. Its root entry is DOM-free, like the other packages' ([ADR-0002](0002-genre-root-entries-are-dom-free.md)); the WebRTC transport lives in its browser entry.
- Signalling is a small hosted worker that swaps WebRTC offers and answers behind a join code: a Cloudflare Worker with a Durable Object per join code, defined and deployed with Alchemy (TypeScript infrastructure as code). Peers use free public STUN servers. There is no TURN server in the first version, so two peers behind symmetric NATs can't connect yet.

**A run starts in step.** Everyone is in the lobby when the run starts; there is no late join. The host sends the run's seed, its config and the content hash with the start message. A peer whose content hash differs refuses to start, with an error naming both hashes. Every peer then calls `start` with the same seed and config.

**Anything that changes the run is a step-scheduled input.** In single-player, the survivors demo picks an upgrade with `engine.modify((world) => chooseUpgrade(world, index))`, and pausing calls `setPaused`. Both run at whatever step the click lands on, which differs per peer. In a lockstep run, an upgrade pick, a pause and a player leaving are part of some step's input, scheduled like any other input, so every peer applies them at the same step. The lockstep engine offers no `modify` and no local pause. `GameLoop.modify` and `setPaused` stay for single-player, and their docs no longer offer `modify` for "a network message".

**A desync stops the run.** Every N steps, each peer hashes its state and sends the hash to the host with its input; the host compares them and relays its own. A mismatch stops the run for everyone, with an error that names the step and every peer's hash. There is no resync. The hash comes from the genre, as the replay tests' hash does today; where it sits in the interface is decided with `@gamekit/net`'s first implementation.

**A drop-out waits, then removes the player.** A disconnected peer, or a hidden tab whose timers are throttled, stops sending input. Stepping waits on the missing input, and every peer shows "waiting for X". After about 10 s, the host removes that player: their removal is an input scheduled for the next undecided step, so their hero leaves at the same step on every peer, and the run continues without them. A removed player can't rejoin that run. With no host migration, a host that drops out ends the run for everyone, since no other peer can decide a step.

**Survivors' co-op rules are the genre's, not this ADR's.** One shared team XP pool, a level-up that pauses everyone until each player has picked, and N players in `World` follow in #25's genre work. Push-puzzle stays single-player.

## Considered Options

- **Rollback netcode.** Each peer predicts the missing inputs, steps on, and rewinds and re-simulates when a real input differs. It feels better at high latency. Rejected: it needs snapshot and restore of a run's state, which [ADR-0007](0007-no-runtime-snapshots.md) rules out, and re-simulating several steps per frame would multiply the cost of a survivors step with hundreds of enemies. A co-op horde game tolerates 50 to 100 ms of input delay; a fighting game would not.
- **A full mesh.** Every peer sends its input to every other peer, and each peer decides on its own when a step is complete. It saves one hop of latency for non-host peers. Rejected: it needs up to six connections for 4 players, each through NAT traversal, and no single peer is the authority on who is in the run. Removing a dropped player would then need the peers to agree on the step it happens at, which is a consensus problem the star avoids. The star also gives desync checks a natural referee.
- **Resync from the host's state after a desync.** Needs state serialization, which ADR-0007 doesn't provide, and would hide arithmetic bugs that ADR-0011 wants found. Stopping with a clear error is enough while the step is exact.
- **A hosted broker such as PeerJS, or copy-pasted offers.** A broker is a third-party dependency on the join path; copy-paste is only fit for a prototype. A worker of our own behind a join code is small and stays in the repo as code.
- **Keep `modify` and broadcast each call.** A closure can't be sent, and even a described change would land at a different step on each peer. Scheduling it as input is the same mechanism the step already has.

## Consequences

- **[ADR-0003](0003-one-fixed-step-clock.md) is amended.** A lockstep run doesn't use the fixed clock's `{ seconds }` path. The lockstep engine passes `{ steps }` budgets, which never clamp or drop, and a step can only wait for its inputs, never be skipped. A hidden tab no longer pauses only its own run: it stalls everyone until the host removes that player.
- **[ADR-0004](0004-one-press-one-step.md) is amended, and ADR-0010's open question on `endFrame` is settled.** On a lockstep peer, the local device source is not the `StepInput` that `GameLoop` reads. The engine samples it on its own schedule, once per step it schedules, calls its `endStep` after each sample and its `endFrame` once per sampling tick, then sends the sample. So one press still reaches exactly one step's input, and every peer applies it once. `GameLoop` reads the buffer of merged inputs, whose `endStep` and `endFrame` don't touch a device.
- **[ADR-0007](0007-no-runtime-snapshots.md) stands.** Delay-based lockstep restores no earlier state, and a desync stops the run instead of resyncing.
- **[ADR-0010](0010-a-game-is-a-simulation-and-a-presentation.md) holds without a contract change.** `GameLoop.frame` with a `{ steps }` budget is the seam the lockstep engine plugs into, `stepIndex` numbers the steps it hashes, and `StepInput.read(stepIndex)` is how merged inputs reach a step. Its open question about making `modify` and pause into step-scheduled inputs is settled above.
- **[ADR-0011](0011-a-step-uses-only-exact-math.md) is what makes this work across browsers.** Lockstep depends on every engine computing the same step, and the desync check is the backstop if one doesn't. The cross-browser Playwright check stays later work in #25.
- **A genre's input becomes per-player.** A lockstep step's input holds every player's input, plus the scheduled actions (picks, pauses, removals). Survivors' `SurvivorsInput` and `World` change for N players in #25's genre work.
- **Two engines in one process is the test setup.** `@gamekit/net`'s tests run a host and a peer, each with its own `GameLoop`, over the in-memory transport, and check that their hashes match under latency, jitter and loss, that a desync is reported with its step, and that a silent peer is removed after the timeout.
- **The signalling worker is infrastructure in the repo.** Deploying it needs a Cloudflare account; the join flow fails with a clear error when the worker can't be reached. Adding TURN later changes only the transport's configuration.
