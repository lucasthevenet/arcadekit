## The game is the domain.

Most game code tangles the rules into the scene graph and the frame loop. arcadekit keeps them apart, in a model you can name, read and test, the way domain-driven design keeps a business's rules apart from its database and its screens.

| Domain-driven design | In arcadekit |
| --- | --- |
| Ubiquitous language | Each part of a game is a class named in its own words: `LevelSolved`, `ChooseUpgrade`, `OfferClosed`. |
| Domain events | `Game.Event`: a fact a run reports, named in the past tense. |
| Commands | `Game.Command`: a decision a player sends, named in the imperative. |
| Invariants | `Game.Rejection`: why the rules refuse a command, named for what is wrong. |
| Aggregate | A run of a `Game.Simulation`, whose state changes only at a step, by its input and its commands. |
| Bounded context | A genre: its rules behind one public file, and its browser half behind another. |
| Adapters | The engine, content, saves, sound and co-op, each provided by a Layer around the rules. |

## Tests that read like the rules.

A scenario is a spec you can run: given a run, after these steps and commands, it reported these events. Write it from the design before the rules exist, and it fails until they are right. No browser, no mocks, no waiting on frames.

```ts
import * as Game from "arcadekit/game";
import * as Scenario from "arcadekit/game/scenario";
import { Schema } from "effect";
import { it } from "vitest";

class DoorOpened extends Game.Event("DoorOpened", { atStep: Schema.Int }) {}

class Door extends Game.Simulation("Door", {
  input: Schema.Struct({ lever: Schema.Boolean }),
  events: [DoorOpened],
  create: (config: { readonly needed: number }) => ({
    needed: config.needed,
    held: 0,
    open: false,
  }),
  step: (door, input, { report, step }) => {
    door.held = input.lever ? door.held + 1 : 0;
    if (!door.open && door.held === door.needed) {
      door.open = true;
      report(new DoorOpened({ atStep: step }));
    }
  },
}) {}

const scenario = Scenario.make(Door);

it("opens once the lever has been held long enough", () =>
  scenario(
    Scenario.given({ needed: 3 }),
    Scenario.step({ lever: true }, 2),
    Scenario.reported(),
    Scenario.step({ lever: true }),
    Scenario.reported(new DoorOpened({ atStep: 2 }))
  ));
```

## Made to be worked on by agents.

An agent does its best work in code it can find by name and check by running. A game written with arcadekit is both.

- **A small shape to learn.** Every game is the same few declarations, so what an agent learns on one game holds for the next, and it finds a part by the name the design gave it.
- **Mistakes the types catch.** Input, events, commands and content are Schemas, so a wrong field fails to compile or to load, with a message that names it.
- **Checks without a screen.** Rules, engines, views and co-op all run in Node. An agent reads what a frame drew and what a peer heard without opening a browser.
- **Failures that repeat.** A run is deterministic: a failing test fails the same way every time, and a bug is a seed and the inputs that found it.

<p class="eyebrow">Multiplayer</p>

## Co-op from the same model.

The rules give the same run on every machine, so co-op adds no second model to keep. Two to four players, each in their own browser, play one run: peers send each other nothing but their inputs and commands, a step runs once every player's input for it is in, and state hashes catch a desync at the step it happens.

## Everything at the edge.

Input, drawing, sound, content and saves are adapters around the rules, each declared once and provided by a Layer. Inside the rules, the world is plain data a step keeps.

<p class="eyebrow">Built on Effect</p>

## Plain rules, Effect around them.

The step is plain code, so it runs fast and the same everywhere. What has a lifecycle around it is Effect. If your app already uses Effect, arcadekit carries the same tools into the game. If Effect is new to you, it is part of the learning curve.

- Every load, save, attach and connection is an Effect, with its errors in its type.
- Events, commands, content and saves are Schemas, so what crosses a boundary is checked.
- A game's parts are services, provided by Layers and closed with their scope.

<p class="eyebrow">Fit</p>

## Is it a fit?

arcadekit asks for a shape: the rules as a deterministic model, and Effect around them. That is a real commitment.

<div class="fit">
<div>

### A strong fit

- **Making games with a coding agent.** The shape is small and every check runs in Node, so an agent can design, build and test in a loop, and show you the results.
- **Developers who think in domains.** Events, commands and rejections in the game's own words, and the rules apart from the screen.
- **Games that need replays, tests or co-op.** Determinism is the default, so all three come with the shape.

</div>
<div>

### Think twice when

- **You want a visual editor.** arcadekit is code first: there is no scene editor and no asset pipeline.
- **Your game needs physics.** There is no physics engine: a collision is what your step computes over a spatial grid.
- **You would rather not use Effect.** It is throughout: its services, Schemas and Layers hold a game together.

</div>
