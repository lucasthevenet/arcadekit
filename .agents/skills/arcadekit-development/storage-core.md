# Plain code: the storage core and hot loops

- **No `effect` import in `src/ecs/`.** It is usable, and tested, with no Effect at all.
- **Nothing is shared between worlds.** A world keeps the names of the components it stores; the module holds no registry. The one module-level value is the counter that numbers component definitions, and that number is never saved, hashed or compared between processes.
- **Columns, not objects.** Numeric data is in typed arrays, one per field. A hot path allocates nothing per entity and makes no Effect per entity: a loop over a query's rows, a plugin's `loops.ts`, `src/ecs/`, and the loops of `@arcadekit/three` that draw. A claim about allocation is measured, as `packages/three/test/Three.test.ts` measures the heap over a frame.
- **Nothing is made from text.** No `eval`, no `new Function`, here or anywhere in the package: a page under a strict Content Security Policy refuses both, and the package runs there as it is. What has to be fast for every kind of column is written out once per kind, as the accessors of `each` are in `src/ecs/component.ts`, which says why that is as fast as generating it: an engine keeps what it learns about a function with its place in the source, so one function for every kind of array is slow and seven that differ in a type are not. The Oxlint rule `arcadekit/no-code-from-text` refuses it in the sources, and `test/Policy.test.ts` plays a game in a process that forbids it.
- **An id is a number only inside the storage core**, which keeps ids in `Float64Array`s and converts an id to its number and back with `idOf` and `entityOf`, in `src/ecs/component.ts` alone: the type `Entity` is no number, and the Oxlint rule `arcadekit/id-casts` refuses an assertion to an id's type anywhere else. A loop over a raw column of ids reads an index with `& INDEX_MASK`, which takes a number's low bits whatever is above them, never a generation with a shift. An array of indexes, a sparse set's members or a change log's entries, may stay 32 bits wide.
- **A raw read asserts**, `pos.x[i]!`, under `noUncheckedIndexedAccess`. That is what `!` is for here, and almost the only place it belongs. It is decided, not a gap: no API of the raw path spares it, since one that checked would be a call per read.
- **A structural change during iteration throws.** Queue it on `Commands`.
- **Iteration order is fixed**: tables in creation order, rows ascending, whichever strategy finds the rows. A change that makes order depend on data breaks replays.
- **Every way to write component data saves it first, inside a transaction.** `set` saves its row, `each` and `eachChunk` save the columns they hand out, once per table and never per entity, but for the terms the query says it only reads. A new way to write does the same when `world._recording` is true, or a refused action leaves a trace and its replay diverges. `test/Transaction.test.ts` has a list of writers that every rollback is checked against: add the new one to it.
- **Every way to write component data notes the write**, for the change queries that watch the component: `this._changed[def.id]?.note(index)` for a row, `noteRows` for rows handed out raw (but for the terms a query only reads), and the accessors of `each` note the rows they assign to. A new way to write does the same, or a change query misses it. `test/Changes.test.ts` checks every writer against a model kept by hand: add the new one to it.
- **Who points at whom is worked out, not stored.** A relation's columns are the truth, saved and hashed like any component's; the index beside them is rebuilt by `load` and is in neither. So every change of a target goes through the world (`_place`, `add`, `remove`, `despawn`), and nothing that reads the index may let the order of its lists show: a despawn goes through relations by name and holders by index.
- **Every way to change the world refuses a frozen one.** `world._frozen` is true while an app's frame stage or its input stage runs. `spawn`, `despawn`, `add`, `remove`, `set`, a singleton's setters and a command check it, and `each` hands out accessors whose setters throw. A new way to change the world checks it too. The random generator is checked once, by `thaw`, which puts it back and throws if it was drawn from: a check in every draw would cost every draw. `test/Frame.test.ts` has a list of changes that a frozen world must refuse: add the new one to it.
- **What a simulation can tell apart is in `world.snapshot()` too**, so that a world which loads one goes on exactly as the world it was taken from. State added to the hash is added to the snapshot in the same change, and read back by `load`, which trusts nothing it reads: a count is checked against the bytes that are left before anything is allocated for it.
- **A snapshot's format is written once and read once**, by `write` and `read` in `src/ecs/format.ts`. A world is a source and a target of them, in `World.snapshotOf` and `World.loading`, and so are the contents a migration works on, in `src/ecs/contents.ts`. What a snapshot holds, its order and what an older format held are changed in `format.ts` alone; a source or a target says where its own data is and checks what it is given. Oxlint refuses the encoding's `Reader`, `Writer`, `readColumn` and `writeColumn` in any other source, with `no-restricted-imports` in `oxlint.config.ts`.
- **What the world holds is emptied by `world.restore()`**, which puts a snapshot back into a world that is in use. State added to the world is reset there in the same change, or a restored world is not what a new one that loaded the snapshot would be. `test/Restore.test.ts` holds the two against each other over random operations, and has a view asked for before a restore throw: an object that is made of the world's tables and handed out notes `world._restored` and refuses to be used after.
- **What a simulation can tell apart is in `world.hash()`**, and nothing else is. State that a system can observe, or that decides what it will observe later, is added to the hash in the change that adds the state, in an order that does not depend on the process: by name, never by id. State nobody can observe (a cache, spare capacity) stays out, or two equal worlds would hash differently.
- **What a game holds beside its components is a store of its world.** A store (`src/ecs/store.ts`, attached with `World._attach`) is the one place that knows how its state is kept: it says what a snapshot holds of it, what the hash covers, what it is at a moment and how to go back to it, and how to take back what a transaction did, and `snapshot`, `load`, `restore`, `hash`, `_capture`, `_rewind` and a rollback ask every store. State an app adds to a game is a store of its own, in the module it belongs to, as the events waiting to be read are in `Event`, the queued actions in `Action` and what change queries have yet to visit in `Save`: never a variable its owner keeps next to the world, and never a new case in the world's own methods. `test/stores.ts` has a store for tests, and `test/Snapshot.test.ts` holds a world's stores to each of these.
- **Where a reader is stays out of the hash.** How far each system has read the events and what its change queries have yet to visit are saved with the world and go back with it, and are not in `world.hash()`: a plugin that only watches must not change the hash of the game it watches. What the frame and input stages have heard is not the game's at all: no store holds it, and a rewind doesn't put it back.
- **Measure.** A change to the storage core or to a query comes with a run of `pnpm --filter arcadekit bench`, before and after, in the pull request. A change to the loops that draw comes with `pnpm --filter @arcadekit/three bench`. `pnpm --filter arcadekit bench:compare <base checkout>` measures the storage core itself against another checkout's, and fails on a variant that is slower by more than the noise; the `Benchmarks` workflow runs it on a pull request, against what it would be merged into. A commit that slows a variant on purpose says so in its message, `Bench-slower: each, eachMany`, with the reason above it.
- **A variant of the benchmark that goes through the storage core alone is in `bench/core.ts`**, which imports `arcadekit/ecs` and nothing else and is what `bench:compare` compares; one that needs an app is in `bench/accessors.ts`. A loop that is timed reads its constants from its own module: an exported one is read through the module each time, which measured a tenth slower.
