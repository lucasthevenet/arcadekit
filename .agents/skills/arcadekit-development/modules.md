# Modules and names

Effect's convention, kept as it is:

- **One module per concept, named in PascalCase**, imported as a namespace: `src/Query.ts` is used as `Query.all(...)`, `Query.without(...)`. A module's functions are named for how they read after the namespace, so `System.tick`, not `System.makeSystem`.
- **Functions, not methods**, for anything a user composes. A function tree-shakes and takes part in `.pipe()`; a method does neither. Methods are for the plain objects a hot loop touches (`view.each`, `commands.spawn`).
- **Constructors are `make`** (`Plugin.make`, `App.make`). A system is `System.tick`, `System.frame` or `System.input`, one for each group of stages. A declaration the user writes once at module level, with a name that identifies it at run time, is `define` (`Component.define`, `Event.define`, `Action.define`). So is the game, `App.define`, which has no name: `App.make` is taken by the app that runs it.
- **Suffixes mean what they mean in Effect**: `Unsafe` for a call that can throw or skips a check (`fiber.pollUnsafe`), `Option` for a result that may be absent, `Exit` for a result returned as a value, where the plain name throws (`Schema.decodeUnknownExit` beside `Schema.decodeUnknownSync`). A call that returns an Effect takes none of them: its caller has `Effect.exit` for the outcome as a value, as for each method of an app.
- **`ByName`** for the variant of a typed call that takes data from outside (`app.dispatchByName`).
- **A file that is no module is camelCase, as Effect 4.1.4 names its own, and `index.ts` is lower case.** They are not namespaces: the storage core's files under `src/ecs/`, and the implementation in an `internal/` folder, whose exports are `@internal`. The folder is `internal/`, never `internals/`, and no file is kebab-case: Oxlint's `unicorn/filename-case` asks for camelCase or PascalCase in a folder of `src/`.
- **Every module is an entry, and an entry makes a promise about what it imports.** A module's file is PascalCase, and its entry is its path: `src/App.ts` is `arcadekit/App`, and `src/net/Session.ts` is `arcadekit/net/Session`, in a lower-case folder of modules whose `index.ts` is an entry too, `arcadekit/net`, and gives them as namespaces. A module named as its folder keeps the folder in its path: `src/browser/Browser.ts` is `arcadekit/browser/Browser`, never `arcadekit/Browser`. `arcadekit` (`src/index.ts`) gives the modules of `src/` together.
- **A module that outgrows its file is split into files, not left long, and keeps its entry.** `packages/arcadekit` holds several domains. A module that is one file stays flat, `src/<Name>.ts`, and its implementation, or what several modules share, goes in `src/internal/<camelCase>.ts`: `src/internal/build.ts` is used by `App`, `net/Session` and `net/Peer`, and `src/internal/outbox.ts` by `Event` and `Timeline`. A module does not move into a folder only because it has internals. A domain of several files is a lowercase folder, `src/<domain>/`, as `src/net/` is: its `src/<domain>/index.ts` is the entry `./<domain>`, each PascalCase submodule `src/<domain>/<Sub>.ts` is the entry `./<domain>/<Sub>`, and what only that domain uses is in `src/<domain>/internal/`. A submodule is never flattened from `src/<domain>/<Name>.ts` to `./<Name>`. A dedicated package of one domain, `packages/three`, keeps its PascalCase public modules flat in `src/`, beside `src/index.ts`, with their implementation in the root `src/internal/`, as Effect's satellite packages such as `@effect/platform-browser` do: a `src/three/` folder would only repeat the package's name. Files under `internal/` are never entries, and `test/Entries.test.ts` holds each of them to be behind one. A part a game would import by itself becomes a PascalCase module and an entry, which the module it came from re-exports. A class or type a module exports is declared in its public file, as `App.FrameChangedWorld` is in `src/App.ts`, so that its reference links there. The folder split before this rule, `src/system/`, is laid out this way when a change touches it. Splitting a module needs no new entry, so nothing is public because a file was long. Each imports Effect and nothing else, and names nothing that only a page has: no `document`, no `requestAnimationFrame`, no `navigator`. `arcadekit/ecs` (`src/ecs/index.ts`) is the storage core and imports nothing at all. A new module gets its entry in `package.json` in the same change, and its line in `src/index.ts`, or in its folder's `index.ts`.
- **An entry is a line of the package's `exports`.** Each subpath of its `package.json` `exports` names its source file under a `source` condition, which Vite and Vitest are given by `tooling/build/source-condition.ts`, so that tests run from the source with no build, and its built files at the same path under `dist/`, `./dist/ecs/index.d.ts` and `./dist/ecs/index.js` for `./src/ecs/index.ts`. The TypeScript compiler builds the package, `tsc -p tsconfig.build.json`: it writes each source file to its own file, bundles nothing, and rewrites a relative import's `.ts` as `.js`. So a file imports another by its own name, `./Color.ts`, and an export's type may be inferred.
- **Every export has a doc comment**, with a `@category`. That is the package's reference, which the site is made from; one marked `@internal` is left off it. The `jsdocs` skill says how one is written.
- **What only a page can use is in `arcadekit/browser`** (`src/browser/`: `arcadekit/browser/Browser`, `arcadekit/browser/Audio`, and what both keep to themselves in `src/browser/internal/`), all of it: the page's display, its devices, its pictures, and what starts a game in it, with the one import of a browser package. New code goes where its imports allow, not where its subject suggests: a page's keyboard is in `Browser`, though it is input. `arcadekit` does not give it, and no other module imports it, so a program that does not run in a page never loads it. The Oxlint rules `arcadekit/entry-imports` and `arcadekit/no-page` check all of this in the sources, and the build writes each source file to its own file, so it imports what the sources do.
- **An entry is named as its namespace is**, and imported whole: `import * as Input from "arcadekit/Input"`, `import * as Browser from "arcadekit/browser/Browser"`, or by its folder, `import { Browser } from "arcadekit/browser"`.
- **What depends on a library a game may not have is a package of its own**, under `packages/`, named `@arcadekit/<library>`: `@arcadekit/three` draws with Three.js. `arcadekit`, Effect and the library are its peer dependencies, never its dependencies, so that a game has one copy of each and a component or a service is the same object in both packages. It imports `arcadekit` by its entries (`arcadekit/Query`, `arcadekit/ecs`), and its own modules are entries too, named as here. The Oxlint rule `arcadekit/entry-imports` checks what it imports. In `packages/three`, `src/Three.ts` is its module and its entry, and re-exports its parts, which are modules beside it (`@arcadekit/three/Scene`, `Renderer`, `Assets`, `Instances`, `Objects`) with their implementation in `src/internal/`; `src/Gltf.ts` is the one for models, which brings the glTF loader of Three.js, and `src/index.ts` gives both.
- **What a game's rules write is in `arcadekit`, never in such a package.** Where a thing is, `arcadekit/Transform3d` and `arcadekit/Transform2d`, and what colour it is, `arcadekit/Color`, are read by the renderer and defined here: a component that lived in the renderer's package would have a server install the renderer to run the rules. Such a package defines no component of its own; it reads the game's.
- **A string that identifies something at run time is prefixed**: `"arcadekit/World"` for a service, `"physics/Position"` for a component. Two services with the same key silently become one. A component's name is its identity in a world, which refuses a second component with a name it already holds.

Import Effect's modules from the package root, `import { Context, Effect, Layer } from "effect"`, and a single function from its module's path, `import { dual } from "effect/Function"`. See [Importing Effect](https://effect.website/docs/v4/getting-started/importing-effect).
