# Modules and names

Effect's convention, kept as it is:

- **One module per concept, named in PascalCase**, imported as a namespace: `src/Query.ts` is used as `Query.all(...)`, `Query.without(...)`. A module's functions are named for how they read after the namespace, so `System.tick`, not `System.makeSystem`.
- **Functions, not methods**, for anything a user composes. A function tree-shakes and takes part in `.pipe()`; a method does neither. Methods are for the plain objects a hot loop touches (`view.each`, `commands.spawn`).
- **Constructors are `make`** (`Plugin.make`, `App.make`). A system is `System.tick`, `System.frame` or `System.input`, one for each group of stages. A declaration the user writes once at module level, with a name that identifies it at run time, is `define` (`Component.define`, `Event.define`, `Action.define`). So is the game, `App.define`, which has no name: `App.make` is taken by the app that runs it.
- **Suffixes mean what they mean in Effect**: `Unsafe` for a call that can throw or skips a check (`fiber.pollUnsafe`), `Option` for a result that may be absent, `Exit` for a result returned as a value, where the plain name throws (`app.tickExit` beside `app.tick`).
- **`ByName`** for the variant of a typed call that takes data from outside (`app.dispatchByName`).
- **A file in a folder of `src/` that is no module is kebab-case, and `index.ts` is lower case.** They are not namespaces: the storage core's files under `src/ecs/`, and the implementation under an `internals/` folder, such as `src/internals/tick-scheduler.ts`. Oxlint's `unicorn/filename-case` refuses any other case there. A test's helpers, the benchmarks and the examples are camelCase.
- **Every module is an entry, and an entry makes a promise about what it imports.** A module's file is PascalCase, and `test/Entries.test.ts` derives its entry from where the file is. A top-level file, `src/App.ts`, is `arcadekit/App`. A module in a folder named as it is, `src/<folder>/<Name>.ts`, is the folder's main module and the entry of its own name, `arcadekit/<Name>`. Any other module in a folder is the entry of the folder and its name: `src/net/Session.ts` is `arcadekit/net/Session`, in a folder of modules that is an entry too by its `index.ts`, `arcadekit/net`. No file under an `internals/` folder is an entry. `arcadekit` (`src/index.ts`) gives the top-level entries' modules together.
- **A module that outgrows its file is split into files, not left long, and keeps its entry.** A module with one public file stays flat, `src/App.ts`, and its implementation goes in `src/internals/<kebab-case>.ts`, beside what several modules share: `src/internals/build.ts` is used by `App`, `net/Session` and `net/Peer`, and `src/internals/outbox.ts` by `Event` and `Timeline`. A module with several public submodules gets a folder of its name: its main module is `src/<folder>/<Name>.ts`, still the entry `arcadekit/<Name>`, each public submodule is `src/<folder>/<Sub>.ts`, the entry `arcadekit/<folder>/<Sub>`, which the main module re-exports, and what only that folder uses is in `src/<folder>/internals/<kebab-case>.ts`. A module does not move into a folder only because it has internals. Files under `internals/` are never entries, and `test/Entries.test.ts` holds each of them to be behind an entry. A class or type the module exports is declared in its public file, as `App.FrameChangedWorld` is in `src/App.ts`, so that its reference links there. The folders split before this rule, `src/system/` and `src/services/`, are laid out this way when a change touches them. Splitting a module needs no new entry, so nothing is public because a file was long. Each imports Effect and nothing else, and names nothing that only a page has: no `document`, no `requestAnimationFrame`, no `navigator`. `arcadekit/ecs` (`src/ecs/index.ts`) is the storage core and imports nothing at all. A new module gets its entry in `package.json` in the same change, and its line in `src/index.ts`, or in its folder's `index.ts`.
- **A package that is one domain keeps its modules flat.** In `@arcadekit/three`, `packages/three`, the public modules are PascalCase files directly in `src/`, `src/Three.ts` and `src/Gltf.ts`, and their internals go in `src/internals/<kebab-case>.ts`. A folder named for the package's own domain, such as `src/three/`, would only repeat the package's name, so none is made.
- **An entry is a line of the package's `exports`.** Each subpath of its `package.json` `exports` names its source file under a `source` condition, which Vite and Vitest are given by `tooling/build/source-condition.ts`, so that tests run from the source with no build, and its built files as `./dist/<name>.d.ts` and `./dist/<name>.js`. `tsdown.config.ts` builds every export from that map, and generates the declarations with the TypeScript compiler (`tsgo`), so an export's type may be inferred.
- **Every export has a doc comment**, with a `@category`. That is the package's reference, which the site is made from; one marked `@internal` is left off it. The `jsdocs` skill says how one is written.
- **What only a page can use is in `arcadekit/Browser`** (`src/Browser.ts`), all of it: the page's display, its devices, its pictures, and what starts a game in it, with the one import of a browser package. New code goes where its imports allow, not where its subject suggests: a page's keyboard is in `Browser`, though it is input. `arcadekit` does not give it, and no other module imports it, so a program that does not run in a page never loads it. The Oxlint rules `arcadekit/entry-imports` and `arcadekit/no-page` check all of this in the sources, and the build writes each source file to its own file, so it imports what the sources do.
- **An entry is named as its namespace is**, and imported whole: `import * as Input from "arcadekit/Input"`, `import * as Browser from "arcadekit/Browser"`.
- **What depends on a library a game may not have is a package of its own**, under `packages/`, named `@arcadekit/<library>`: `@arcadekit/three` draws with Three.js. `arcadekit`, Effect and the library are its peer dependencies, never its dependencies, so that a game has one copy of each and a component or a service is the same object in both packages. It imports `arcadekit` by its entries (`arcadekit/Query`, `arcadekit/ecs`), and its own modules are entries too, named as here. The Oxlint rule `arcadekit/entry-imports` checks what it imports. In `packages/three`, `src/Three.ts` is its module and its entry, `src/Gltf.ts` the one for models, which brings the glTF loader of Three.js, and `src/index.ts` gives both.
- **What a game's rules write is in `arcadekit`, never in such a package.** Where a thing is, `arcadekit/Transform3d` and `arcadekit/Transform2d`, and what colour it is, `arcadekit/Color`, are read by the renderer and defined here: a component that lived in the renderer's package would have a server install the renderer to run the rules. Such a package defines no component of its own; it reads the game's.
- **A string that identifies something at run time is prefixed**: `"arcadekit/World"` for a service, `"physics/Position"` for a component. Two services with the same key silently become one. A component's name is its identity in a world, which refuses a second component with a name it already holds.

Import Effect's modules from the package root, `import { Context, Effect, Layer } from "effect"`, and a single function from its module's path, `import { dual } from "effect/Function"`. See [Importing Effect](https://effect.website/docs/v4/getting-started/importing-effect).
